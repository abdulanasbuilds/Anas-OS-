# ANAS OS — Transcript-Derived Operating Model

This document records the two complementary ideas incorporated into ANAS OS.

## Track A — Level-5 Personal/Company Operating System

ANAS should retain strategic context, capture workflows, turn proven work into reusable skills, keep bounded learnings, generate briefings, surface commitments, and improve workflows from feedback.

Implemented as native capabilities: skills, memory, workflow capture, advisor, research briefing, content workflow, chief-of-staff analysis, scheduler, and governed system-improvement proposals.

The last mile remains human: taste, consequential communication, ownership, and high-risk decisions stay under human authority.

## Track B — Agent/Harness Execution System

ANAS should treat coding agents and harnesses as interchangeable executors. Work follows a controlled loop: `plan → authorize → execute → verify → evidence → handoff/escalate`. Harnesses may use files, shell, git, model APIs, and other tools only inside ANAS contracts and permissions.

Implemented as the native Agent System: registry, contracts, skills, harnesses, tool permissions, context, planning, orchestration, execution, verification, recovery, evaluation, auditability, cost/observability, and human escalation.

## Synthesis

The two tracks are not separate products. Track A supplies persistent operating context and repeatable workflows; Track B supplies the governed execution workforce. The kernel connects them.

Self-improvement is proposal-first: measure → diagnose → propose → review → approve → adopt. It may improve skills and workflows, but it cannot silently change Constitution, authority, security, legal, financial, or destructive boundaries.

## Provider independence

Neither track may require a specific commercial provider. ANAS owns the contracts and policy; providers and harnesses are adapters. Local/open options are preferred where practical, paid services are opt-in, and provider failure must degrade safely.
